# 세션 토폴로지 비교 — 10 프로세스 vs 단일 프로세스

> 상태: **결정 완료 — B안 채택 (2026-07-29)** · 관련: [launchpad-design.md](./launchpad-design.md) · [cli-spec.md](./cli-spec.md)
>
> **이 문서는 앞선 설계문서 §3.1의 결론(프로세스 분리 채택)을 재검토한다.** 당시 근거는 "공급사 혼용 시 격리가 유리하다" 한 줄이었고, 검증이 부족했다.
>
> **결정**: B안(단일 프로세스 + 페르소나)을 채택한다. 단 프로세스는 시스템 전체에 1개가 아니라 **프로필당 1개**다. 프로필 `bateam` 이 게이트웨이 프로세스 하나를 가지고 그 안에 10개 페르소나가 상주한다. 상세는 [launchpad-design.md §3](./launchpad-design.md) 참조.

## 2. 판단의 핵심 — 세션이 들고 있어야 할 상태가 있는가

프로세스를 나누는 이득은 **각 프로세스가 오래 유지해야 할 고유 상태가 있을 때** 생긴다. 그래서 먼저 물어야 할 것은 "Lucas 세션이 메모리에 무엇을 들고 있는가"다.

| Lucas 세션이 가진 것 | 실제 소재 |
| --- | --- |
| 페르소나 (시스템 프롬프트) | `roles/lucas-tech-lead.md` — **디스크. 매 요청 재조립 가능** |
| 대화 히스토리 | `~/.hermes/state/lucas/*.jsonl` — **디스크. 재기동해도 복원됨** |
| 모델·공급사 설정 | `config/agents/lucas.yaml` — **디스크** |
| API 커넥션 | HTTP keep-alive — 공유 가능, 역할 고유 아님 |

**메모리에만 존재하는 고유 상태가 없다.** LLM 에이전트는 요청마다 `시스템 프롬프트 + 히스토리`를 조립해 API를 호출하고 결과를 저장하는, 사실상 무상태 구조다.

상주가 절약하는 것은 **프로세스 콜드스타트뿐**이다.

| 항목 | 소요 (추정) |
| --- | --- |
| Node 프로세스 기동 + SDK 로드 | 200–500ms |
| 페르소나 파일 읽기 + 프롬프트 조립 | 5–20ms |
| **LLM 응답** | **2,000–20,000ms** |

콜드스타트는 전체 응답 시간의 **2% 미만**이다. 상주의 주된 명분이 여기서 무너진다.

> 숫자는 실측이 아니라 일반적인 Node/LLM 환경 기준의 추정치다. 1단계 구현 후 실측으로 갱신할 것.

## 3. A안 — 10 프로세스 상주

### 3.1 실제로 이득인 지점

| 이득 | 현재 요구사항에서의 유효성 |
| --- | --- |
| **런타임 격리** — 역할이 서로 다른 언어/네이티브 바인딩을 쓸 때 | ✗ 전부 HTTP API 호출. 격리할 대상이 없다 |
| **장애 격리** — 한 역할의 크래시가 전체에 전파되지 않음 | △ 유효하나, 무상태라 재시작 비용이 낮아 영향이 작다 |
| **메모리 누수 격리** — 누수가 한 역할에 갇힘 | △ 유효. 단 단일 프로세스도 주기적 재시작으로 대응 가능 |
| **역할별 독립 배포** — Lucas만 새 코드로 교체 | ✗ 코드가 공통이라 해당 없음 |
| **역할별 리소스 상한** — 개별 rate limit·타임아웃 | ✗ 단일 프로세스 내에서도 동일하게 구현된다 |
| **장시간 작업** — 역할이 도구 실행·빌드 등을 수행 | ✗ 1차 비범위. 도입 시 재검토 (§7) |

**6개 중 실질 유효는 2개뿐이고, 그 2개도 무상태 구조에서는 위력이 크지 않다.**

### 3.2 비용

**메모리.** Node 프로세스 하나가 SDK를 로드한 상태의 RSS는 대략 80–120MB다. 10개면 **유휴 상태로 0.8–1.2GB**를 점유한다. 개발용 맥에서 IDE·브라우저와 함께 쓰면 체감되는 크기다.

**운영 표면.** launchd 라벨 11개, 포트 10개, 로그 파일 11개, 헬스체크 대상 11개. 장애 시 "어느 세션이 죽었나"를 먼저 가려야 한다.

**IPC.** Gateway ↔ 세션 간 로컬 HTTP가 필요하다. 직렬화, 타임아웃, 재시도, 세션 미기동 시 처리, 공유 시크릿 인증 — 전부 구현·테스트 대상이다. **B안에서는 이 계층 자체가 없다.**

**포트 관리.** 자동 배정, `state.json` 고정 기록, 충돌 감지(`doctor`) — CLI 스펙의 상당 부분이 포트 때문에 존재한다.

## 4. B안 — 단일 프로세스 + 페르소나 전환

### 4.1 동작

```ts
// 요청 하나의 전 과정 — 프로세스 경계를 넘지 않는다
async function handle(agentId: string, threadKey: string, text: string) {
  const agent    = registry.get(agentId);              // config/agents/<id>.yaml (캐시)
  const persona  = await personas.load(agent.persona); // roles/<id>.md (캐시 + mtime 감시)
  const history  = await store.read(agentId, threadKey);
  const provider = providers.get(agent.provider);      // 공급사별 인스턴스 재사용

  const result = await provider.complete({
    system: buildSystem(persona, defaults),
    messages: [...history, { role: 'user', content: text }],
    model: agent.model,
    temperature: agent.temperature,
  });

  await store.append(agentId, threadKey, text, result.text);
  return result;
}
```

역할 구분은 **`system` 프롬프트와 `provider`/`model` 선택**으로 끝난다. 이것이 "페르소나로 관리한다"의 실체다.

### 4.2 이득

- **메모리 80–120MB 총.** A안 대비 1/10.
- **IPC 계층 소멸.** Gateway와 세션이 같은 프로세스이므로 HTTP·포트·직렬화·인증이 전부 사라진다.
- **운영 단위 1개.** launchd 1개, 로그 1곳, `hermes status`가 프로세스 하나만 본다.
- **역할 추가에 재기동 불필요.** `config/agents/*.yaml`을 감시하면 핫 리로드가 가능하다. A안은 새 프로세스 기동 + plist 등록 + Gateway 라우팅 갱신이 필요하다.
- **역할 간 토론 구현이 쉽다.** 설계문서에서 3단계로 미룬 "Oscar가 Lucas의 답을 반박" 같은 흐름이 **함수 호출**로 끝난다. A안에서는 세션 간 HTTP 호출 + 순환 방지 + 타임아웃 전파를 다뤄야 한다.
- **`--tag` 부분 소집이 불필요해진다.** 유휴 비용이 사실상 0이므로 "안 쓰는 역할을 내려둔다"는 개념 자체가 사라진다.

### 4.3 비용

- **크래시가 전체를 멈춘다.** 단 무상태라 launchd `KeepAlive`가 수 초 내 되살리고, 진행 중이던 요청만 유실된다.
- **한 요청이 이벤트 루프를 막으면 전체가 느려진다.** 실제로는 전부 네트워크 I/O 대기라 문제되기 어렵다. CPU를 쓰는 작업(대용량 파싱 등)이 생기면 워커 스레드로 분리한다.
- **SDK가 한 런타임에 공존한다.** `@anthropic-ai/sdk` + `openai` 정도는 충돌하지 않는다. 네이티브 바인딩이 필요한 공급사가 추가되면 재검토 대상이다.
- **역할별 리소스 상한을 직접 구현해야 한다.** 프로세스 경계가 공짜로 주던 것을 세마포어·큐로 대체한다. 다만 A안도 동시 호출 제어는 어차피 필요하다.

## 5. 시나리오 검증

| 시나리오 | A. 10 프로세스 | B. 단일 프로세스 |
| --- | --- | --- |
| Lucas·Grace에 동시 질문 | 각 프로세스가 병렬 처리 | `Promise.all` 병렬 처리 — **동일** |
| 역할 1명 추가 | yaml + `apply` → 프로세스 기동 + plist + 라우팅 갱신 | yaml 추가 → **핫 리로드** |
| Grace 페르소나 문서 수정 | grace 세션만 재시작 | mtime 감지 후 **재시작 없이 반영** |
| terra 공급사 장애 | grace만 실패 | grace 요청만 실패 — **동일** (공급사별로 격리됨) |
| 프로세스 크래시 | 해당 역할만 중단 | 전체 수 초 중단 후 자동 복구 |
| 메모리 누수 | 누수 역할만 재시작 | 전체 재시작 (주기적 예방 재시작으로 대응) |
| 10명 동시 회의 소집 | 프로세스 10개 병렬 | 비동기 10개 병렬 — **동일** |
| Oscar가 Lucas 답변 반박 | 세션 간 HTTP + 순환 방지 | **함수 호출** |
| 유휴 시 메모리 | 0.8–1.2GB | 80–120MB |
| 맥 재부팅 후 복구 | 11개 LaunchAgent 기동 | 1개 기동 |

**"동일"이 다섯 줄이다.** 병렬성·공급사 격리처럼 A안의 이점으로 기대했던 항목 상당수가 실제로는 차이를 만들지 않는다. 비동기 I/O가 이미 그 역할을 하기 때문이다.

## 6. 권고 — **B안 (단일 프로세스 + 페르소나)**

근거를 순서대로 정리하면,

1. **역할 세션에 프로세스 경계가 지킬 만한 고유 상태가 없다.** 페르소나도 히스토리도 설정도 전부 디스크에 있다. 프로세스 분리가 격리하는 대상이 실질적으로 없다.
2. **A안 이점 6개 중 4개가 현재 요구사항에서 무효**이고, 남은 2개(장애·누수 격리)도 무상태 구조에서는 재시작이 저렴해 위력이 작다.
3. **IPC·포트·헬스체크 계층 전체가 사라진다.** CLI 스펙의 포트 자동 배정, `state.json` 포트 고정, `doctor`의 포트 충돌 검사가 모두 불필요해진다. 구현·운영·문서가 함께 줄어든다.
4. **3단계 목표인 역할 간 토론이 훨씬 쉬워진다.** Oscar가 Lucas의 답을 반박하는 흐름은 B안에서 함수 호출이고, A안에서는 분산 시스템 문제다. 이건 미래 요구를 앞당겨 반영하는 게 아니라, **이미 로드맵에 있는 항목의 난이도가 갈리는** 문제다.
5. **10명 상주 비용 문제(CLI 스펙 §8-2)가 소멸한다.** 유휴 비용이 없으니 `--tag`로 일부만 올리는 운영 기교도 필요 없다.

### 결정이 뒤집히는 조건

다음 중 하나라도 성립하면 A안을 다시 검토한다.

- 역할이 **도구를 실행**하기 시작할 때 (코드 실행, 빌드, 브라우저 조작) — 프로세스 격리가 안전 경계가 된다
- 특정 역할이 **로컬 모델이나 네이티브 바인딩**을 쓸 때
- 한 역할이 **분 단위 장시간 작업**을 점유해 다른 역할을 막을 때
- 역할별로 **다른 배포 주기·권한**이 필요해질 때

## 7. B안 채택 시 변경점

### 7.1 문서 반영 현황 — **완료 (2026-07-29)**

| 문서 | 반영 내용 |
| --- | --- |
| `launchpad-design.md` **2판** | 토폴로지 B안 · 프로필 `bateam` 도입 · 구성도 단일 프로세스 · `src/session/` 삭제 후 `src/gateway/` 통합 · LaunchAgent 11개 → **프로필당 1개** · IPC/포트 서술 전면 삭제 |
| `cli-spec.md` **3판** | 프로필을 **게이트웨이 단위**로 재정의 · `--port` 및 포트 관련 항목 전면 삭제 · `start`/`stop`을 프로세스 층과 페르소나 층으로 분리(§7.2) · `bateam` 기준 예시로 교체 · 부록에 삭제 목록 정리 |
| 유휴 비용 문제 | **해소** — 프로세스가 하나이므로 "일부만 상주" 개념 자체가 사라짐 |

### 7.2 수명주기 명령이 두 층으로 나뉜다

프로세스가 프로필당 하나이므로 "Grace를 중지"가 프로세스 종료를 뜻할 수 없다. 층위를 분리한다.

```bash
hermes stop --profile bateam    # 게이트웨이 프로세스 종료 — 10명 전부 응답 불가
hermes agent disable grace      # Grace만 비활성 — 나머지 9명 정상 · 재기동 없음
hermes agent enable  grace      # 재활성화 (즉시 반영)
```

`agent disable grace` 후 `/grace`를 부르면 **"Grace는 현재 비활성입니다"** 라고 안내된다. A안에서는 세션을 내린 뒤 `/grace`를 부르면 **응답 없음**이었고, 그게 의도된 중지인지 장애인지 구분되지 않았다. 이 편이 낫다.

### 7.3 유지되는 것

아래는 토폴로지와 무관하므로 그대로 간다.

- **Provider 추상화** (설계문서 §5) — 오히려 B안에서 더 중요해진다. 한 프로세스가 여러 공급사를 다루므로 인터페이스 통일이 필수다.
- **페르소나를 `roles/*.md`에서 읽는 방식** (§4)
- **Keychain 자격증명 관리** (§8)
- **Slack 단일 앱 + 페르소나 게시** (§6) — 결론적으로 **런타임 구조와 Slack 구조가 일치**하게 된다. 봇 하나가 여러 페르소나로 말하고, 프로세스 하나가 여러 페르소나를 연기한다.
- **에이전트 1명 = YAML 1개** (CLI 스펙 §5)
- **`hermes chat <id>`** — 이제 실행 중인 프로세스에 붙는 게 아니라 같은 코드를 직접 호출하므로 더 단순해진다

## 8. 결정 (2026-07-29 확정)

1. **B안 채택.** 관련 문서 개정 완료.
2. **프로세스 단위는 "시스템 전체 1개"가 아니라 "프로필당 1개"로 한다.** 프로필 `bateam`이 게이트웨이 프로세스 하나를 갖고, 그 안에 10개 페르소나가 상주한다. 이 문서의 §4~§6 논거는 그대로 유효하다 — 프로필 내부에서 역할을 프로세스로 쪼개지 않는다는 것이 요지이기 때문이다.
3. **프로필 분리는 A안으로의 회귀가 아니다.** 프로필 경계는 *역할* 경계가 아니라 *게이트웨이·Slack 앱·자격증명* 경계다. 프로필이 늘어도 역할 수만큼 프로세스가 늘지 않는다.
4. **전환 여지 명시.** §6의 "결정이 뒤집히는 조건"을 유지한다. Provider 추상화와 에이전트 레지스트리가 그대로 재사용되므로, A안 전환 비용은 IPC 계층 추가분에 국한된다.
